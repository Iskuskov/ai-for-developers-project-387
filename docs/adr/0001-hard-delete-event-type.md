# Жёсткое удаление типа встречи с блокировкой при предстоящих записях

Типы встреч, которые владелец больше не проводит, должны исчезать из списка и со страницы записи гостей. Записи ссылаются на тип по `eventTypeId`, а хранилище in-memory: вместе с удалением типа исчезает возможность получить его название для списка записей. Мы решили удалять тип навсегда (`DELETE /event-types/{id}` → 204) и запрещать удаление, пока у типа есть предстоящие Записи (409 `EventTypeInUseError`); прошедшие Записи удалению не мешают и не сохраняются. Обоснование: при блокировке предстоящих записей «осиротевших» названий в `/bookings` не бывает, поэтому снапшот названия в Записи не нужен, а архивация с флагом усложняет контракт и хранилище без выгоды.

## Considered Options

- **Архивация (скрытие типа флагом):** отклонено — тип остаётся в хранилище и контракте, хотя владельцу и гостям он больше не нужен; в in-memory хранилище без операций обновления это лишняя сложность.
- **Удаление всегда + снапшот названия в Записи:** отклонено — потребовало бы менять модель Записи и контракт ради названий прошедших записей, которые `/bookings` всё равно не показывает.
- **Жёсткое удаление + 409 при предстоящих записях:** принято — гость не теряет актуальные записи, а контракт остаётся минимальным.

## Consequences

- Seed-типы (`greeting`, `consultation`, `code-review`) удаляются на общих основаниях: отдельной защиты нет.
- Старая прямая ссылка гостя `/booking/:id` на удалённый тип показывает дружелюбное сообщение вместо падения.
