## Сценарий использования

### Владелец календаря

1. Открывает раздел управления типами встреч.
2. Создаёт тип встречи: указывает название, описание и длительность.
3. Тип встречи сразу становится доступен гостям для записи.
4. После того как гость записался, владелец видит встречу в списке предстоящих: показываются записи всех типов, отсортированные по дате и времени.

### Гость

1. Открывает главную страницу и выбирает тип встречи.
2. Видит календарь на ближайшие 14 дней со свободными слотами: длительность слота равна длительности выбранного типа встречи.
3. Выбирает день и свободное время.
4. Вводит имя и email, подтверждает запись.
5. Занятый слот становится недоступен для записи — для всех типов встреч.

## Ограничения

- Авторизации и личных кабинетов нет: владелец календаря один и задан заранее, гость записывается без регистрации.
- Окно записи — 14 календарных дней, начиная с сегодняшнего; окно сдвигается с течением времени.
- Рабочие часы владельца: 09:00–18:00 (Europe/Moscow).
- Шаг доступных стартов слотов — 30 минут.
- Одно и то же время нельзя занять дважды: пересечения интервалов запрещены, включая частичное наложение разных типов встреч. Встреча может начинаться в момент окончания предыдущей. Правило действует и для одновременных запросов.
- Данные хранятся в памяти процесса: перезапуск приложения сбрасывает все записи.

## Агент в GitHub (OpenCode)

К репозиторию подключён агент [OpenCode](https://opencode.ai/docs/github/): он выполняет задания из комментариев к issue и PR внутри GitHub Actions.

- **Событие**: комментарий к issue или PR (`issue_comment` и `pull_request_review_comment`, только `types: [created]`). Воркфлоу — `.github/workflows/opencode.yml`.
- **Модель**: `opencode/big-pickle` (бесплатная: воркспейс Hexlet Students отключил доступ API-ключей к платным моделям, бесплатные mimo/nemotron недоступны — проверено локально); ключ модели лежит в секрете `OPENCODE_API_KEY` (Settings → Secrets and variables → Actions).
- **Назначение**: объяснить issue, ответить на вопрос по репозиторию, исправить мелочь отдельной веткой/PR.
- **Команды вызова** (`mentions`): `/oc <задание>` или `/opencode <задание>` — например, `/oc explain this issue` или `/oc fix this`.
- **Кто может вызывать**: доверенные участники — владелец и коллабораторы репозитория. Комментарии ботов игнорируются; авторы из недоверенных форков отсекаются условием джоба и не доходят до шагов, где доступны секреты.
- **Права и безопасность**: джобу исполняет OpenCode GitHub App в стандартном OIDC-режиме (не вариант `use_github_token` без App): воркфлоу запрашивает `contents: read` и `id-token: write` (обмен OIDC-токена на токен установки App), checkout — с `persist-credentials: false`; таймаут джоба — 25 минут (задачи агента занимают 0.5–7 минут — зависание не живёт дольше 15); параллельные прогоны ограничены группой `concurrency` на issue — новая команда отменяет устаревшую, а «пустые» прогоны от комментариев ботов изолированы в отдельную группу и никого не отменяют. В `opencode.json` интерактивные вопросы агенту запрещены (`question → deny`) — все вопросы агент задаёт комментарием в треде; чтение внешних каталогов разрешено (`external_directory → allow`), чтобы агент не зависал на permission-запросах, на которые в безлюдном прогоне некому ответить.
- **Диагностика**: лог прогона стримится живьём на вкладке Actions в веб-интерфейсе (строка `asking {permission: ...}` = агент ждёт разрешения — признак зависания); `gh run view --log` показывает лог шага только после его завершения.
- **share**: `manual` (в `opencode.json`) + `share: "false"` в воркфлоу (без явного запрета экшен автопубликует сессии публичных репозиториев) — сессии агента не публикуются автоматически, но любую можно расшарить вручную ссылкой из Console: в сессии виден полный ход работы агента, а не только итоговый ответ.
- **Результаты**: ответ агента — комментарием в issue; полный лог прогона — на вкладке Actions.

## Автотриаж обращений (OpenCode)

Воркфлоу `.github/workflows/opencode-triage.yml` разбирает новые issue автоматически:

- **Событие**: `issues` (`opened`, `reopened`) — триггер без команды; для передачи задания агенту используется `prompt` (требование событий `issues`).
- **Модель**: та же `opencode/big-pickle`, ключ в секрете `OPENCODE_API_KEY`.
- **Что делает**: применяет скилл triage — определяет суть обращения, ставит одну метку (`needs-triage`, `needs-info`, `wontfix` или `ready-for-agent`, если обращение полностью понятно) и оставляет комментарий-разбор с рекомендацией следующего шага.
- **Фильтры**: автор — доверенный участник (владелец/коллаборатор), не бот; **тикеты, подготовленные скиллами to-spec/to-tickets (метка `ready-for-agent`), повторно не разбираются** — джоб скипается по метке.
- **Права и лимиты**: `contents: read` + `id-token: write` (OIDC), `persist-credentials: false`, таймаут 25 минут, `concurrency` на issue с изоляцией пустых прогонов.
- **Бюджет запусков на PR**: перед вызовом модели воркфлоу считает прогоны агента по данному issue/PR через историю Actions (токен агента историю не перепишет); лимит — переменная репозитория `OPENCODE_PR_BUDGET` (по умолчанию 3, меняется админом). Исчерпание: отдельный шаг без модели публикует `limit_exhausted`, последний SHA и ссылку на логи со статусом «нужен человек»; отказ прогона публикуется с причиной `timeout`/`infra`/`agent_failed`. Новый PR — новый бюджет.

## Авторевью PR (OpenCode)

Воркфлоу `.github/workflows/opencode-review.yml` ревьюит каждый pull request автоматически:

- **Событие**: `pull_request` (`opened`, `synchronize`, `reopened`); runs на обычном CLI (не экшен с App) — OIDC этому сценарию не нужен.
- **Ревьюер независим**: отдельный запуск, не продолжение сессии реализации; читает REVIEW.md (критерии календаря), спеку/тикет/обращение по ссылкам из PR, дифф и результаты CI; текст ревью публикует отдельный шаг `gh pr comment`. Код ревьюер не правит; комментарий ревью сам не запускает исправление — между замечанием и правкой стоит команда человека (`/oc`).
- **Фильтры**: ветки только своего репозитория; чужие боты — мимо; PR собственного агента (opencode-agent) ревьюится — иначе авторевью агентских PR никогда бы не сработало.
- **Права и лимиты**: `contents: read`, `issues: read`, `actions/checks/statuses: read`, `pull-requests: write` (комментарий); таймаут 25 минут; `concurrency` на PR — новое ревью отменяет устаревшее.
- **Ссылки недоступны или изменение выходит за согласованный объём** — авторевью отмечает это замечанием.

## Аудит по расписанию (OpenCode)

Воркфлоу `.github/workflows/audit.yml` регулярно проверяет живое приложение Lighthouse'ом и разбирает отчёт агентом:

- **События**: `schedule` (cron `17 3 * * *`, GitHub считает в UTC → ежедневно 06:17 по Москве) + `workflow_dispatch` (ручной запуск с входом `mode`: `real`/`sample`); файл в основной ветке.
- **Права**: `contents: read` + `id-token: write` (стандартный режим App — issue создаёт токен установки App); checkout с `persist-credentials: false`.
- **Лимиты**: `timeout-minutes: 20`; `concurrency: opencode-audit` — параллельные аудиты не накапливаются.
- **Сбор данных**: адрес приложения — переменная репозитория `APP_URL` (прежний работающий адрес на Render); перед аудитом приложение прогревается (Free-план спит).
- **Где результат**: исходный отчёт — артефакт прогона (`audit-reports/`, каталог в `.gitignore` — отчёты в коммиты не попадают); вывод агента — комментарий в журнальном issue [#18](https://github.com/Iskuskov/ai-for-developers-project-387/issues/18) (находки/их отсутствие + ссылки на прогон и артефакт).
- **Дедуп**: перед созданием задачи агент ищет существующие issues — повторная находка не создаёт дубликат.

### Результаты прогонов

1. **Real** ([прогон](https://github.com/Iskuskov/ai-for-developers-project-387/actions/runs/44095970894)): performance 0.98 / accessibility 0.87; агент создал 5 задач по находкам: [#13](https://github.com/Iskuskov/ai-for-developers-project-387/issues/13) (контраст), [#14](https://github.com/Iskuskov/ai-for-developers-project-387/issues/14) (уровни заголовков), [#15](https://github.com/Iskuskov/ai-for-developers-project-387/issues/15) (блокирующий CSS), [#16](https://github.com/Iskuskov/ai-for-developers-project-387/issues/16) (неиспользуемый CSS), [#17](https://github.com/Iskuskov/ai-for-developers-project-387/issues/17) (неиспользуемый JS).
2. **Повтор real** ([прогон](https://github.com/Iskuskov/ai-for-developers-project-387/actions/runs/44097195074)): те же 5 находок распознаны как дубликаты (ссылки на #13–#17, дублей нет); появившаяся новая находка корректно создана отдельным issue [#19](https://github.com/Iskuskov/ai-for-developers-project-387/issues/19) (отсутствие кэширования статики).
3. **Sample (учебный отчёт)** ([прогон](https://github.com/Iskuskov/ai-for-developers-project-387/actions/runs/44101242905)): агент создал задачу с пометкой «учебная» — [#20](https://github.com/Iskuskov/ai-for-developers-project-387/issues/20) (это не подтверждённый дефект приложения); первая попытка учебного отчёта с находкой, дублирующей #15, корректно завершилась отказом от дубликата.

### Личные выводы о работе агента

- **Что потребовало уточнений**: первая формулировка промпта не отделяла «нет данных» от «дефектов нет» (приложение на Render спит — аудит без прогрева дал бы ложное «всё плохо» или пустой отчёт); добавил прогрев и явное правило «недоступность = нет данных». Дедуп пришлось описать явно: без указания «ищи существующие задачи» агент плодил бы дубликаты каждый прогон.
- **Что изменили в настройках/постановке**: находку учебного отчёта изначально посадил на тот же аудит (`render-blocking-resources`), что уже был в реальных задачах — агент корректно отказался дублировать #15; поменял учебную находку на непересекающуюся (`tap-targets`), чтобы сценарий создания задачи был виден. Лимит бюджетов и пиннинг версии экшена (форк) — из предыдущего шага, здесь пригодились сразу.
- **Что приятно удивило**: агент сам связал находку повторного аудита с существующими задачами и сам завёл журнальное issue с полной структурой ссылок (артефакт → прогон → задачи) без дополнительных указаний.

## Установка

Требуется [mise](https://mise.jdx.dev/) (`curl https://mise.run | sh`) — он подтянет Java 25, Node.js 26, pnpm и остальные инструменты по `mise.toml`.

```bash
git clone https://github.com/Iskuskov/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise install       # инструменты
mise run install   # зависимости бекенда и фронтенда
hk install --mise  # git-хуки: линтеры и проверка формата коммитов
```

## Использование

```bash
mise run dev:backend   # бекенд: http://localhost:8080
mise run dev:frontend  # фронтенд: http://localhost:5173

# или оба сервера фоном:
mise daemons start

# все проверки (линтеры, тесты, сборка) — то же, что запускает CI:
mise run check
```

Полный список задач: `mise tasks ls`. Рабочие правила для агентов — в [AGENTS.md](AGENTS.md).
